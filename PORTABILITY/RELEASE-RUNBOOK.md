# Guarded release and distribution runbook

## Before changing anything

1. Establish live repository and edition state.
2. Read `COMMITS-PENDING.md` and inspect the worktree.
3. Work in an isolated candidate for substantive source or machinery changes.
4. Obtain supervisor approval for edition identity and publication scope.

## Candidate validation

- Build twice and compare generated bytes.
- Validate all six skill folders.
- Check semantic-route and Thai-place counts.
- Render and inspect Word output when it changes.
- Run `git diff --check`.
- Review modified, deleted and untracked paths.
- Record user-facing changes, edition reasoning and exact pending payload.

## Supervisor publication

The supervisor runs `pipeline-registry/push.bat` and reads its entire preflight.
Typing `PUSH` authorises only the displayed payload and the documented
post-push sequence.

The workflow must stop on:

- stale or invalid generated output;
- missing Control parity;
- unavailable Shift or cloud preflight;
- failed commit, rebase or push;
- local/origin mismatch;
- missing or failed GitHub validation;
- failed Shift regeneration;
- failed cloud copy or verification.

## Cloud semantics

The cloud publisher copies the complete `pipeline-registry/Blueprint` tree to
the three approved destinations. It excludes Python caches, updates or adds
files, and does not delete remote extras. Each destination is then checked
one-way from local source to remote.

Google Drive permits duplicate names. A duplicate warning is not normal
success: inspect with `rclone dedupe DESTINATION --dedupe-mode list`. Any
deduplication that deletes redundant objects requires supervisor approval.

## Confirmation record

Record:

- final commit SHA;
- local/origin equality;
- GitHub run URL and conclusion;
- Shift check result;
- matching-file count and zero-difference result for each cloud destination;
- any bounded cleanup or exception.
